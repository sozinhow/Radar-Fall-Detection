## Tensor contract

Each inference uses a trailing, contiguous 60-record / 3-second buffer at
20 Hz. The host creates float32 `[1,60,13]`: seven normalized base features in
this order: `x, y, z, dop_idx, range_m, azimuth_deg, elevation_deg`; then
`xyz_delta_mag`, four clipped centred five-frame rolling standard deviations
for `x/y/z/range_m`, and `range_centered`. Inference is invoked at record 60
and every 15 fresh records after that. Output class order is `walking`,
`standing`, `sitting`, `fall`.

## Reset behaviour

The buffer is cleared and no prediction is displayed after a missing scheduled
record, duplicate frame ID, non-finite/non-integer value, non-monotonic
timestamp, or timestamp discontinuity. The structured reason taxonomy is:
`missing_record`, `duplicate_frame_id`, `invalid_value`, `timestamp_gap`, and
`other` (connection, tracking loss, or queue-overflow lifecycle clears).

The GUI's **last reset** line shows a human-readable code and detail; **reset
counters** are cumulative for the current GUI process. This makes the cause of
a buffer that repeatedly stops below 60 visible without weakening the reset
policy. A high `missing` count means a 20 Hz scheduler tick had no fresh
decoded target report; high `ts_gap` means the scheduled timing departed from
50 ms beyond the configured tolerance. The GUI must then show `0 / 60` until
sixty fresh records arrive. It displays probabilities as diagnostic information
only; it does not trigger a fall alert.

### Live missing-record diagnostics

`missing_record` now has a separate live-stream detail: `no_fresh_frame`
(a recent target-list report contained no targets), `queue_empty` (no fresh
decoded target was waiting at the tick), `late_frame` (the queued target arrived
after the scheduled tick tolerance), `tracking_inactive`, or `other_missing`.
The panel retains the last reason during recovery, shows cumulative reset
counters, and adds the current/max queue depth plus the most recent arrival
jitter. A repeated `queue_empty` while the normal collector says “tracking”
is the expected signature of the current issue: tracking remains true for its
0.5-second grace period but no new target is available for one or more strict
50 ms inference ticks.

### Diagnostic tolerance mode

The **Allow one held tick (diagnostic only)** checkbox is off by default. When
enabled, the first missing tick is recorded but does not immediately erase the
buffer. No sample is copied or fabricated. The inference state becomes
`disabled`, produces no tensor/probability output, and requires 60 subsequent
fresh records before a valid causal window and inference can resume. A second
missing tick before recovery clears the buffer normally. This mode is solely
for distinguishing a one-off scheduling/arrival jitter event from an actual
stream interruption; it does not change the model, tensor contract, or alert
policy.

### Live handoff-grace evaluation — 2026-07-28

A read-only 10-second host diagnostic session on `/dev/cu.usbmodem11402` used
the same parser, queue, handoff grace, and causal engine flow as the GUI. It
decoded 437 valid TinyFrame messages and accepted 201 first-target records.
Results: **0 total resets**, `queue_empty=0`, `late_frame=0`,
`tracking_inactive=0`, `no_fresh_frame=0`; maximum queue depth was 29; positive
lateness was observed once at 1.8 ms (mean/max 1.8 ms); no held-tick event was
used. The causal buffer reached `60 / 60` and remained valid.

Conclusion: the former tick-versus-enqueue race was the dominant observed
host-side reset cause, and the bounded 20 ms grace removed it in this session
without a late-frame trade-off. Queue depth reflects bursty host delivery, not
an invalid input; because no reset category now dominates, no additional
host-side scheduling or tracking change is justified from this evidence.

### Session summary and primary stability fix

Use **Copy session stats** in the GUI (or stop a CSV collection) to obtain one
copyable line containing total reset categories, all missing sub-cause counts,
maximum queue depth, mean/maximum positive lateness, and held-tick events.

The primary host-side cause identified by scheduling-path inspection is
**queue starvation at the strict consumer tick**: the prior loop could clear
the buffer at a 50 ms deadline just before the next GUI poll decoded and
enqueued a fresh target. The host consumer now waits for a bounded 20 ms
handoff grace before recording `queue_empty`. It appends no sample during that
wait; a queue that remains empty after the deadline still resets fail-closed,
and a frame arriving after the same bound is reported as `late_frame` rather
than accepted as fresh.
